2. PURPOSE & SCOPE
Purpose
The Allergen & Dietary Safety Schema defines the authoritative data contract for the allergens domain within the Restaurant AI System's Master Knowledge Base.
This is a safety-critical document. Incorrect allergen information can result in anaphylaxis, severe medical emergencies, and profound legal liability. The purpose of this schema is to establish a mathematically deterministic, un-guessable, and auditable system for tracking food safety data.
Scope: What This Document Controls
 * The explicit, standardized representation of the 14 EU-regulated allergens.
 * The 4-tier allergen state model (CONTAINS, MAY_CONTAIN, FREE_FROM, UNKNOWN).
 * The deterministic mapping of allergen safety profiles to menu items via item_id.
 * The fail-closed fallback mechanisms when data is missing or conflicting.
 * The exact phrasing boundaries and constraints imposed on the AI Engine.
 * The lifecycle and re-verification triggers that invalidate safety records.
Scope: What This Document Explicitly Does NOT Control
 * Dietary Preferences: Tags such as VEGAN, HALAL, or KETO_FRIENDLY are lifestyle and marketing labels governed by KB-SPEC-005. They are architecturally separated from physiological safety data.
 * Full Ingredient Lists: This schema tracks the presence of specific biological hazards, not exhaustive recipe instructions or general ingredient databases.
 * Medical Diagnoses: The system does not assess the severity of a guest's allergy or recommend medical action.

4. DOMAIN PHILOSOPHY / NON-NEGOTIABLE PRINCIPLES
 * UNKNOWN IS NEVER SAFE: If the system cannot explicitly verify the absence of an allergen, it must report UNKNOWN. The AI is strictly prohibited from inferring safety from absence of warnings.
 * Explicit Verification: FREE_FROM is an active assertion requiring verification evidence. It is never the default state.
 * Fail Closed: If two authoritative sources conflict (e.g., website says safe, supplier says contains), the system evaluates to UNKNOWN and flags an admin review.
 * Identity Determines Safety: Changing a menu item's name or category alters its item_id (per KB-SPEC-005). This automatically orphans the old safety matrix and resets the new item to UNKNOWN, forcing human re-verification of the modified recipe.
 * Separation of Preference and Hazard: A dietary tag (e.g., VEGAN) does NOT automatically populate the safety matrix (e.g., milk: FREE_FROM). Safety requires explicit allergen-specific assertions.
5. DOMAIN ARCHITECTURE
The allergens domain exists at the top level of the Master JSON Schema (tenant-scoped) and consists of an array of explicitly mapped safety matrices.

    {

Architectural Rationale for Centralization
Storing the eu_14 matrix centrally under "allergens" rather than nesting it deep inside "menu" catalogs ensures that safety data can be managed, audited, and versioned by distinct administrative roles (e.g., a Head Chef) without entangling it in daily marketing/pricing updates.
6. CRITICAL EU-14 CATEGORY DEFINITION
The system strictly enforces the explicit evaluation of the 14 major food allergens recognized by EU regulations. Inventing new categories, altering standard names, or merging categories is prohibited.
The JSON schema MUST represent these exactly as the following standardized snake_case keys:
 * celery
 * cereals_containing_gluten
 * crustaceans
 * eggs
 * fish
 * lupin
 * milk
 * molluscs
 * mustard
 * peanuts
 * sesame
 * soybeans
 * sulphur_dioxide_and_sulphites
 * tree_nuts
7. ALLERGEN STATE MODEL (ENUM)
For every item_id, each of the EU-14 allergens must be assigned one of exactly four states.
Important Pipeline Distinction: The four states defined below are strictly FINAL OPERATIONAL states for the canonical JSON. Transient "candidate" states (e.g., a suspected FREE_FROM derived from scraping) exist exclusively within the pre-verification ingestion pipeline and MUST NOT be persisted into the active Knowledge Base until verification requirements are met.
| State | Semantic Meaning & Evidence Policy | AI Interpretation |
|---|---|---|
| CONTAINS | The allergen is explicitly established as a deliberate ingredient. | "This item contains [allergen]." |
| MAY_CONTAIN | Explicitly flagged for cross-contact risk (e.g., shared fryers, facility warnings). | "This item may contain traces of [allergen] due to cross-contamination." |
| FREE_FROM | Evidence Policy: Only allowed when an authorized verification source explicitly establishes absence under the venue's declared preparation controls. | "This item is verified free from [allergen]." |
| UNKNOWN | No conclusive safety data exists. Distinguishes between Unverified (data not yet collected) and Verified Unknown (venue explicitly cannot confirm absence). | "I cannot verify if this item contains [allergen]." |
Rule on Ambiguity
FREE_FROM \ne UNKNOWN.
If a menu says "Contains Milk," the system maps milk to CONTAINS and the remaining 13 allergens to UNKNOWN. It does NOT map them to FREE_FROM unless the source explicitly declares "Nut-Free, Gluten-Free," etc., meeting the evidence threshold.

9. ITEM LINKAGE & RE-VERIFICATION TRIGGERS
The item_id serves as the cryptographically stable primary key connecting safety data to the product.
The Cryptographic Safety Reset
As defined in KB-SPEC-005, item_id is a hash of venue_id + catalog + category + item_name.
 * If a restaurant renames "House Salad" to "House Salad with Walnuts", the hash algorithm generates a completely new item_id.
 * The old allergen record mapping to the old item_id is orphaned and pruned.
 * The new item_id has no existing allergen record.
 * The system automatically defaults all 14 allergens for the new item to UNKNOWN and sets verification_status to UNVERIFIED.
 * This deterministically forces a human admin to review and approve the safety profile of the new/renamed dish.
10. SOURCE & PROVENANCE
Every allergen matrix entry requires traceable lineage to prove why a safety state is asserted.
| Field Name | Description | Allowed ENUMs / Format |
|---|---|---|
| source_type | How the data was acquired. | OFFICIAL_WEBSITE, PDF_MENU, SUPPLIER_DOC, HUMAN_VERIFICATION |
| source_url | Origin link (if applicable). | HTTPS URL. Must be omitted if not applicable (e.g., HUMAN_VERIFICATION). |
| verified_by | Identity of the approver. | UUID of the admin user, or system actor ID. |
| verification_timestamp | When the claim was established. | UTC RFC 3339 String. |
11. VERIFICATION MODEL & CONFLICT RESOLUTION
Verification States
 * UNVERIFIED: The matrix was populated by an automated scraper, but has not cleared the human/heuristic safety threshold.
 * VERIFIED: The matrix provenance and state assignments have been approved.
Crucial Semantics of VERIFIED:
A matrix can be marked VERIFIED even if all 14 allergen states evaluate to UNKNOWN. This simply means a human has verified that the venue genuinely does not know the allergen profile. The VERIFIED tag at the matrix level NEVER implies "verified safe"; it only implies "verified as an accurate reflection of the venue's knowledge."
Source Conflict Resolution (Fail-Closed)
If two sources conflict (e.g., Website: FREE_FROM peanuts. Supplier Doc: MAY_CONTAIN peanuts):
 * The Normalization Engine detects the contradiction.
 * The system forces the state of that specific allergen to UNKNOWN.
 * The entire item's verification_status is demoted to UNVERIFIED.
 * The item is flagged with a CONFLICT warning in the Admin Dashboard, suspending AI usage of its safety data until manually resolved.
12. DIETARY TAG SEPARATION (CRITICAL BOUNDARY)
KB-SPEC-005 permits marketing tags like VEGAN.
Architectural Rule: The system MUST NOT automatically translate dietary tags into allergen safety states.
 * A VEGAN tag does not automatically set milk to FREE_FROM.
 * A VEGETARIAN tag does not automatically set fish to FREE_FROM.
Reasoning: "Vegan" is a preparation preference. It does not legally guarantee the absence of severe cross-contact with milk proteins in a shared kitchen. Allergen safety states must be evaluated on their own explicit merits.
13. AI / RAG SAFETY CONTRACT
The RAG index and AI generation layer must adhere to strict constraints based on the ENUM states.
Retrieval (RAG) Filtering vs. Final Authorization
 * If a guest asks: "I have a peanut allergy, which dishes can I eat?"
 * RAG Vector Query MUST filter strictly by: eu_14.peanuts == "FREE_FROM".
 * It MUST NOT retrieve items where the state is UNKNOWN or UNVERIFIED.
 * Important: Retrieval \ne Final Safety Authorization. Successfully retrieving an item tagged FREE_FROM from the vector index is purely data fetching. The AI must still pass the response through Phase 1 conversational safety guardrails before presenting it to the guest.
Permitted AI Phrasing
 * For CONTAINS: "Yes, the Steak Frites contains milk (in the béarnaise sauce)."
 * For MAY_CONTAIN: "The venue states that the fries may contain traces of peanuts due to shared fryers."
 * For FREE_FROM: "Based on the menu data, the House Salad is verified free from tree nuts."
 * For UNKNOWN: "I do not have verified information regarding eggs in the House Burger. Please consult the restaurant staff directly before ordering."
Critical AI Prohibitions
The LLM prompt constraints must explicitly forbid the AI from:
 * Inferring allergen absence from the omission of the word in a description (e.g., "The description only says beef and potatoes, so it's dairy-free" is a banned hallucination).
 * Applying "common sense" to recipes (e.g., assuming a standard pizza contains gluten if the matrix says UNKNOWN).
 * Providing medical advice or guarantees of zero-cross-contamination unless a FREE_FROM state is explicitly backed by a supplier/admin certification.
14. NULLABILITY & MISSING DATA
In the raw scraped payload:
 * If an allergen key is missing, the Normalization Engine MUST inject it and set the value to "UNKNOWN".
 * null, "", or omitted keys are strictly forbidden in the final, canonical JSON payload for the EU-14 matrix.
Rule of Sparsity vs. Canonicalization: UNVERIFIED/raw candidate data may be sparse; canonical operational data MUST always contain exactly 14 allergen keys.
A compliant, canonical eu_14 object always contains exactly 14 keys mapping to one of the 4 strict ENUM values.
15. NORMALIZATION PIPELINE
Unstructured text must be deterministically mapped.
 * "Contains milk, eggs, and wheat." \rightarrow milk: CONTAINS, eggs: CONTAINS, cereals_containing_gluten: CONTAINS. All others: UNKNOWN.
 * "Allergy friendly / Allergy menu." \rightarrow Does not map to any FREE_FROM state. Maps everything to UNKNOWN as it lacks specificity.
 * "Gluten-Free" \rightarrow Evaluates to a candidate cereals_containing_gluten: FREE_FROM within the pre-verification pipeline. Candidate states are transient. It MUST NOT become an operational FREE_FROM in the canonical schema until explicit verification/provenance requirements (Section 10) are fulfilled and approved.
 * Ambiguous Generic Terms: A phrase like "Made in a facility that processes nuts" MUST NOT be automatically expanded into specific EU-14 states (peanuts, tree_nuts) by the scraper. It must remain UNKNOWN and be flagged for explicit human mapping to prevent dangerous guessing.
16. MULTI-TENANT SECURITY
Allergen records are scoped within the venue container in the Master JSON Document.
 * Cross-tenant data leakage is prevented via PostgreSQL Row-Level Security on venue_id.
 * The item_id hash incorporates venue_id, mathematically preventing Venue A's safety record from accidentally binding to Venue B's menu item.

19. INVALID EXAMPLES
Example A: Implicit Nullability & Missing Keys
{
  "item_id": "itm_999",
  "eu_14": {
    "milk": "CONTAINS",
    "peanuts": "FREE_FROM"
    // Missing 12 other keys
  },
  "verification_status": "VERIFIED"
}

 * Why it fails: Structural validation for canonical operational data requires exactly 14 keys. The normalizer must intercept this sparse candidate data and fill the remaining 12 keys with "UNKNOWN" before it is permitted into the operational database.
Example B: Invented States
{
  "item_id": "itm_111",
  "eu_14": {
    "milk": "TRACE_AMOUNTS"
  }
}

 * Why it fails: "TRACE_AMOUNTS" is not a valid ENUM. It must be mapped to "MAY_CONTAIN".

23. FINAL NON-NEGOTIABLE PRINCIPLES
 * UNKNOWN IS NEVER SAFE: Absence of evidence is not evidence of absence. UNKNOWN always evaluates to unsafe.
 * Explicit Verification Required: FREE_FROM is an active assertion requiring verification evidence. Candidate states are transient.
 * No AI Safety Inference: The AI must never deduce allergen absence from ingredient lists, dietary tags, or cuisine types.
 * Identity Dictates Safety: If an item changes its name or hierarchy, it is a new item. Safety profiles do not silently transfer to modified recipes.
 * Fail Closed: Any conflict in data, parsing error, or ambiguity defaults to UNKNOWN and requires human intervention. Canonical data MUST strictly contain exactly 14 keys.
